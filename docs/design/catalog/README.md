# KS design catalog (visual hash registry)

Every reusable visual surface in **forgesdlc-kitchensink** is tracked with a stable **three-letter hash** (`/^[A-Za-z]{3}$/`), **three distinct letters** unless `hash_exception_reason` is set in the registry, and a **design contract** (Markdown) or explicit **`family-covered`** reference.

## Canonical files

| File | Role |
|------|------|
| [visual-registry.yaml](visual-registry.yaml) | Source of truth for hashes, sources, contracts, screenshots |
| [visual-registry.generated.json](visual-registry.generated.json) | Normalized JSON (regenerated by `check-visual-catalog.mjs`) |
| [visual-inventory.generated.json](visual-inventory.generated.json) | Source scan output |
| [visual-inventory.generated.md](visual-inventory.generated.md) | Human-readable inventory summary |
| [visual-registry-coverage.md](visual-registry-coverage.md) | Counts by type/status/contract (from check) |
| [contract-template.md](contract-template.md) | Template for new contracts |
| [page-types/Ks-page-type-design-guidelines.md](page-types/Ks-page-type-design-guidelines.md) | Page-type IA, density, and trust guidance |
| [ONTOLOGY.md](ONTOLOGY.md) | Classification and page-type principles |

Subfolders (`layouts/`, `pages/`, `components/`, …) hold contracts and optional screenshots.

## Hash markers (HTML)

Each **dominant visual root** should emit:

```html
hash="Hbk" data-ks-hash="Hbk" data-ks-type="layout" data-ks-name="layout-handbook"
```

Python: `ks_hash_attrs` in [`components/ks_hash_attrs.py`](../../components/ks_hash_attrs.py).  
Layout/page resolution: [`components/ks_catalog_hashes.py`](../../components/ks_catalog_hashes.py) reads `visual-registry.generated.json`.

React: `ksVisualAttrs` from [`react/ksVisualAttrs.ts`](../../react/ksVisualAttrs.ts) spread onto the component root.

## Crawler contract (regions)

Every **Kitchen Sink–emitted** visual region root (layout shell, page `<main>`, navigation chrome, footers, ToC rails, product nav, etc.) should expose:

- `hash="<Hhh>"` and `data-ks-hash="<Hhh>"` where `<Hhh>` is the three-letter id from [`visual-registry.yaml`](visual-registry.yaml) / [`visual-registry.generated.json`](visual-registry.generated.json)
- `data-ks-type` — registry `type` (`layout`, `page`, `layout-preview`, `chrome-region`, `react-primitive`, …)
- `data-ks-name` — stable kebab-case slug from the registry

Use **one outer root per logical region** (not every nested `div`). Layout shells use `layout_shell_attrs`; handbook/showcase `<main>` uses `page_main_attrs` / `ks_page_attrs`; shared chrome uses `chrome_region_attrs("<slug>")` in [`components/ks_catalog_hashes.py`](../../components/ks_catalog_hashes.py) (see registry rows with `type: chrome-region`). Consumer-built handbooks pick up hashes when their `kitchensink` submodule includes an up-to-date `visual-registry.generated.json`.

## Tooling (standalone from UX auditor/scorer)

From repo root:

```bash
python3 generator/build-showcase.py
node tools/design-catalog/inventory-ks-visuals.mjs --repo . --out docs/design/catalog/visual-inventory.generated.json
node tools/design-catalog/check-visual-catalog.mjs --repo . --registry docs/design/catalog/visual-registry.yaml --showcase showcase
```

One-shot refresh of inventory inside the checker (still offline):

```bash
node tools/design-catalog/check-visual-catalog.mjs --repo . --registry docs/design/catalog/visual-registry.yaml --showcase showcase --refresh-inventory
```

Bulk-insert **deterministic vs AI-review** headings for stateful contracts (layouts, chrome, pages, layout-previews)—content is synthesized from [`tools/design-catalog/lib/contract-governance-blocks.mjs`](../../../tools/design-catalog/lib/contract-governance-blocks.mjs):

```bash
node tools/design-catalog/apply-contract-governance-sections.mjs --registry docs/design/catalog/visual-registry.yaml --repo . --dry-run
node tools/design-catalog/apply-contract-governance-sections.mjs --registry docs/design/catalog/visual-registry.yaml --repo . --write
```

Refresh **Expected look** / **Responsive behavior** from slug-keyed blurbs ([`tools/design-catalog/lib/contract-element-blurbs.mjs`](../../../tools/design-catalog/lib/contract-element-blurbs.mjs))—targets duplicated slabs detected by `contract-specificity.mjs`; requires regenerated [`visual-registry.generated.json`](visual-registry.generated.json):

```bash
node tools/design-catalog/apply-element-specific-blurbs.mjs --repo . --registry-json docs/design/catalog/visual-registry.generated.json --dry-run
node tools/design-catalog/apply-element-specific-blurbs.mjs --repo . --registry-json docs/design/catalog/visual-registry.generated.json --write
```

Checker flags:

| Flag | Purpose |
|------|---------|
| `--refresh-inventory` | Run `inventory-ks-visuals.mjs` before validating |
| `--strict-contract-governance` | Warn when stateful contracts omit **Deterministic** / **AI** review headings (`layout`, `page`, `chrome-region`, `layout-preview`) |
| `--strict-contract-placeholders` | Fail on `TBD` / `TODO` / `FIXME` stub bullets (default: one summary warning with count) |
| `--verbose-contract-placeholders` | Emit one warning per contract that still uses stub bullets |
| `--allow-minimal-showcase` | Skip Shw/Gly density guards (for tiny fixture repos) |
| `--no-strict-inventory` | Do not cross-check `visual-inventory.generated.json` |

Optional:

```bash
node tools/design-catalog/allocate-visual-hash.mjs --suggest 5
node tools/design-catalog/capture-showcase-screenshots.mjs --repo . --serve-showcase --update-registry --mirror-to-showcase
node tools/design-catalog/changed-visual-contracts.mjs
bash tools/design-catalog/verify-bad-fixture.sh
```

Screenshot capture (alternate: external server): `--base-url http://127.0.0.1:4173/` with root serving `showcase/`. See [`screenshots/README.md`](screenshots/README.md).

`verify-bad-fixture.sh` asserts `check-visual-catalog.mjs` exits **1** on the synthetic bad registry under [`tools/design-catalog/fixtures/bad-visual-catalog/`](../../tools/design-catalog/fixtures/bad-visual-catalog/).

**Rule:** scripts under `tools/design-catalog/` **must not** invoke `analyze-website-ux.mjs` or `score-website-ux.mjs`.

### Consumer sites (prod HTML checks)

After rebuilding a consumer site against an updated `kitchensink/` submodule, verify **`hash` / `data-ks-hash`** in generated or live HTML:

- Guide: [consumer-site-hash-verification.md](consumer-site-hash-verification.md)
- Script: `node tools/design-catalog/check-consumer-hashes.mjs` (`--url`, `--file`, or `--dir`, optional `--strict`)

Do not claim public hosts reflect a new KS revision without sampling **current** raw HTML (local build or `curl`).

## Screenshot conventions

- Registry `screenshot_status`: `planned` | `captured` | `missing` | `blocked` | `not-applicable`
- For `planned`, `missing`, or `blocked`, provide at least one of `screenshot_url`, non-empty `notes`, or `screenshot_reason` (enforced by `check-visual-catalog.mjs`).
- Hosted desktop PNG pattern: `https://ks.forgesdlc.com/showcase/screenshots/{HASH}.png`  
- Mobile captures (when produced): same directory `{HASH}.mobile.png` (mirrored under `showcase/screenshots/` when using `--mirror-to-showcase`).
- Phase 06 capture (local, no remote fetch for validation):

```bash
python3 generator/build-showcase.py
cd tools/design-catalog && npm ci && npx playwright install chromium
node capture-showcase-screenshots.mjs --repo ../.. --serve-showcase --update-registry --mirror-to-showcase
```

## Maintenance workflow (visual change) — Prompt 10 checklist

Use this for **any** merge that changes how KS looks, behaves, or documents governed surfaces.

1. **Identify** affected hash(es) from `visual-registry.yaml`, or record why no hash applies (e.g. purely internal refactor with no visual surface).
2. **Edit** [visual-registry.yaml](visual-registry.yaml) — `source_paths`, `status`, `aliases` / `parent_hash` when deprecating; keep **global hash uniqueness** and three **distinct** letters unless `hash_exception_reason` is set.
3. **Edit** the Markdown contract under `docs/design/catalog/**/` — expected look, states, a11y, changelog when behavior changes.
4. **Preserve** hash for compatible refinements; **allocate** a new hash for breaking anatomy or identity (`node tools/design-catalog/allocate-visual-hash.mjs`).
5. **Emit** `hash` / `data-ks-hash` (and `data-ks-type` / `data-ks-name` where used) on visual roots — Python `ks_hash_attrs` / catalog helpers; React `ksVisualAttrs` / `ksReactPrimitiveAttrs`.
6. **New design Markdown under `docs/design/`** (outside `docs/design/catalog/`): add the path to **Kdt** `source_paths` in `visual-registry.yaml` so inventory ↔ registry checks stay aligned.
7. **Regenerate** [visual-inventory.generated.json](visual-inventory.generated.json) after moving or adding sources:  
   `node tools/design-catalog/inventory-ks-visuals.mjs --repo . --out docs/design/catalog/visual-inventory.generated.json`
8. **Validate** with a built showcase and React bundle when markers or primitives matter: run `showcase-react-app` `npm run build` if needed, then `python3 generator/build-showcase.py`, then  
   `node tools/design-catalog/check-visual-catalog.mjs --repo . --registry docs/design/catalog/visual-registry.yaml --showcase showcase`
9. **Screenshots** — update `screenshot_status` / capture when the canonical appearance changes (`capture-showcase-screenshots.mjs` when hosting `showcase/`).
10. **UX audits** — findings may cite `docs/design/catalog/...` by hash; update contracts when remediation touches governed visuals.
11. **CI** — the `design-catalog` workflow runs inventory, catalog check, forge-autodoc tests, and auditor tests; keep it green before merge.

### PR hygiene

- Prefer **one logical catalog change per PR** (registry + contracts + markers) when possible.
- Do **not** copy hashes or rows from kit “example” registries — authority is always this repo plus `inventory-ks-visuals` output.
- After adding files under `showcase-react-app/` that **inventory lists**, extend **Kra** `source_paths` in `visual-registry.yaml`.
